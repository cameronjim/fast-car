# The racer app: a web dashboard and control panel for the car (built overnight 2026-11-10 to 11-11)

**Nothing here has run on the Jetson or the car.** The car was off and untouched. Everything is
tested against a fake docker, systemd and ROS layer on the Mac (see "What is and is not verified").
The first real run is the install in "First install on the Jetson" below, with the wheels off the
ground and nothing armed.

## What it is for

Four things that kept going wrong in real sessions:

| Pain | What the app does about it |
|---|---|
| After every power cycle someone had to ssh in and restart the stack | `racer-stack.service` starts the stack at boot (LiDAR and VESC, no cameras), once the disk check passes. Opt-in setting, ON after the first install. |
| The disk filled to 100 percent, the recorder died, the launch shut itself down | Disk check before anything records, bag folder sizes and a delete button, and a disk guard that sheds load before the disk is full (below). |
| Battery voltage and VESC faults were only visible over ssh | Both are on the dashboard and in the pre-drive checks, with per-cell voltage. |
| Receiver or Jetson power drops caused confusion | Uptime and "just booted" in the checks, and the agent notices an unclean shutdown (no clean stop marker) and writes it in the action log. |
| No one-click way to start gap follow, mapping, localisation, stop | The control panel, and a big STOP ALL button that is always on screen. |

## Safety (also shown in the UI)

- **The app never publishes `/drive` or `/drive_raw`, never reconfigures or bypasses the RC mux,
  and never replaces the kill knob.** Arming still needs the knob. Layer 1 is the only guarantee
  (`claude-docs/05-safety.md`); the app is not a safety layer.
- The only thing the app starts that can move the car is a driving launch (`gap_follow`,
  `wall_follow`, `tracker_node`, `park`), exactly the processes the runbook already starts by hand.
  They publish `/drive_raw`, and `/drive_raw` reaches the wheels only through `safety_node`.
- **STOP ALL is a software stop.** It sends SIGINT to the driving launch, the same as Ctrl-C in the
  runbook. The stack keeps running and recording, `safety_node` sees `/drive_raw` go silent and
  brakes. Wi-Fi can drop, the phone can lag. The knob is the stop that always works.
- A driving run needs the pre-drive checks green, or an explicit override that needs a typed reason
  and is written to the action log.
- **Invariant 5 (every run is logged).** The agent refuses to start a driving launch unless
  `car-stack` is running and its `ros2 bag record` is running (checked with `docker top`), and no
  override can change that. The same goes for a disk under 5 GiB: the recorder would die mid-run.
- The UI code is read-only towards ROS: its foxglove client only subscribes. `guard.test.ts` fails
  the build if any UI source calls an advertise, send, service or parameter function, or names
  `/drive_raw`.
- LAN only, token auth, whitelisted actions only (below). STOP ALL deliberately needs no token (it
  can only make the car quieter, and a phone with a stale token must still be able to stop it); it
  is still LAN only and logged with the caller's address.

## Architecture

```
phone / laptop browser ---- http :8080 ----> racer-agent (host, systemd, user racer)
        |                                        |  docker run / exec / kill (fixed argv lists)
        |                                        |  systemctl is-active, sudo systemctl reboot|poweroff
        |                                        |  ws client (read only) -> foxglove_bridge :8765
        +---- ws :8765 (foxglove protocol, read only) ------------------------+
                                              car-stack container (ROS 2)   car-camera container
```

Decisions, with the reason:

- **The agent runs on the Jetson host, not in the stack container.** It has to start and stop that
  container (and the camera container) and read systemd and sysfs. Putting it in the stack would
  mean the thing that restarts the stack lives inside it. It is a separate process under systemd, so
  a stack crash never takes it down.
- **ROS-side values come through the foxglove websocket, not a status node in the stack.** The
  stack is what drives the car, and every node added to it is one more thing that can break it.
  `foxglove_bridge` already runs there on port 8765 and the browser UI uses the same socket, so the
  agent is just a second, read-only subscriber: no launch file edits, no rebuild, and it keeps
  working whichever launch started the stack. The cost is a tiny hand-written CDR decoder for the
  two std_msgs types the checks need (`Float32`, `String`). Everything else is only counted, which
  gives message rates for `/scan`, `/pose` and `/odom/wheel`. If the bridge is down the checks go
  red ("no ROS connection"), which is the right answer.
- **Python, FastAPI and uvicorn, pinned with uv** (`agent/uv.lock`, exact versions in
  `pyproject.toml`), like the other tools. The web UI is TypeScript, Vite and Preact (about 40 kB
  gzipped), exact versions in `package.json` and `package-lock.json`. The foxglove client is the
  official `@foxglove/ws-protocol`, with `@foxglove/rosmsg` and `@foxglove/rosmsg2-serialization`
  decoding real CDR with the schemas the bridge advertises, so the UI understands every message
  type with no hand-written decoder. The agent serves the built `dist/`; CI builds it, and
  `install.sh` builds it on the Jetson (npm if present, otherwise a pinned node container).
- **Where it lives.** `claude-docs/02-repo-layout.md` has no slot for an app. `tools/` is where
  host-side scripts and services already live (`tools/jetson_heartbeat` is the systemd pattern this
  copies), so it is `tools/racer_app/{agent,web,deploy,find_car.py}`. `tools/pyproject.toml` got a
  `norecursedirs` entry so the existing `tools` test run does not collect it; the agent has its own
  uv project and its own CI gate (`run_python_tests.sh`, 90 percent line coverage).
- **Vehicle numbers come from `config/vehicle_params.yaml`.** The LiDAR mount (x 0.285 m, yaw pi
  today), the body outline, the steering limit and the throttle full scale are read by the agent
  (`GET /api/vehicle`) and the UI draws with those. Invariant 2: the UI has no copy of them. A null
  field comes back as null and the UI says it is not drawing the scan instead of guessing.
- **Cameras are duty-cycled in the browser.** `foxglove_bridge` has no per-subscription rate limit,
  and a 720p JPEG stream is several MB/s over Wi-Fi. The UI subscribes, takes one frame, drops the
  subscription, waits 0.7 s and subscribes again: about one or two frames a second, no sustained
  stream.

## The whitelist: every thing the agent can run

Nothing takes a command string. A profile has to be a key of a table in `commands.py`, a map has to
be a file the agent found itself, a raceline has to be one it listed, a name has to match a strict
regex. Unknown JSON fields are rejected. A test asserts that whatever the API is asked to do, the
host only ever runs `docker`, `systemctl is-active racer-heartbeat.service`, and the two `sudo -n
/usr/bin/systemctl reboot|poweroff` commands.

| Button | What the agent runs |
|---|---|
| Start stack | `docker run -d --name car-stack --network host --user UID:GID --group-add gpio --group-add dialout --device /dev/ttyUSB0 --device /dev/ttyTHS1 -e HOME=/tmp -v <pwm sysfs> x2 -v ~/car:/workspace -w /workspace/ros_ws car:local bash -lc "... exec ros2 launch racer_bringup car_teleop.launch.py lidar:=true vesc:=true [mapping:=true] [localization:=true map:=...]"`, the runbook command flag for flag. A `--device` line is left out when its box is unticked (docker refuses a missing device). Refuses on under 5 GiB free, an unbuilt workspace, a missing image or device. |
| Stop stack | `docker kill -s INT car-stack`, wait up to 30 s, `docker kill` if it lingers, `docker rm`. SIGINT and not `docker stop`: the runbook "Stopping" table shows SIGTERM leaves the PWM channels enabled at neutral. |
| Restart | Stop, then start with the flags it was running with (or new ones). |
| Start cameras | `docker run -d --name car-camera --runtime nvidia ... cameras.launch.py usb_device:=/dev/videoN` with the `docker/car/README.md` flags. The USB device is found by `/sys/class/video4linux/video*/name` containing "Global Shutter" (the capture node, index 0). Needs 10 GiB free. |
| Stop cameras | SIGINT, wait, rm, as above. |
| Gap follow, wall follow, park, tracker | `docker exec -d car-stack bash -c "echo $$ > /tmp/racer-drive.pid; echo MODE > /tmp/racer-drive.mode; source ...; exec ros2 launch racer_control gap_follow.launch.py profile:=P > /tmp/racer-drive.log 2>&1"`. `exec` keeps the pid, so the pid file names the ros2 process. The tracker runs `ros2 run racer_control tracker_node --ros-args -p raceline_path:=... -p pose_frame:=map` (`tracker.launch.py` only forwards `raceline_path`, and no launch file was edited). |
| STOP ALL | `docker exec car-stack bash -c 'kill -INT $(cat /tmp/racer-drive.pid)'` (after checking `/proc/PID/cmdline` is a ros2 process), escalating to TERM and KILL if it lingers. A STOP that lands while a start is in flight kills that start too. |
| Park, three-point turn, abort | `ros2 service call /park_node/start`, `/park_node/three_point_turn`, `/park_node/abort` (`std_srvs/srv/Trigger`). Abort has no checks in its way. |
| Save map | `ros2 service call /slam_toolbox/save_map slam_toolbox/srv/SaveMap` into `data/maps/NAME` (refuses to overwrite). |
| ML policy | `ros2 launch racer_bringup policy.launch.py ...`, enabled only for a policy directory that passes the node's own checks. See below. |
| Delete bag | `rmtree` of one folder directly under the bag directory (name regex, no symlinks, not the one being recorded, name typed to confirm). |
| Reboot, Shut down | Stops driving, cameras and the stack cleanly (SIGINT) first, then `sudo -n /usr/bin/systemctl reboot` or `poweroff` two seconds later. The sudoers drop-in allows exactly those two commands. |
| Autostart box | Creates or removes `/var/lib/racer-app/autostart.enabled`, which `racer-stack.service` has as a `ConditionPathExists`. |

**ML policy (updated with `residual-v1-2026-11-11.md`).** The button is disabled with the reason
until a directory under `data/policies/` passes `python3 -m racer_policy.check`, run inside the
car image with the repo mounted: the same `racer_policy.deploy.load_deployment` that `policy_node`
runs at startup (contract checksum and version, the live `vehicle_params` version, the
observation schema, the sidecar settings), so the app only offers a policy the node will not
refuse. The old check was `load_contract` alone, which accepts a policy trained against another
`vehicle_params` version and lets the node refuse it later. `policy.launch.py` must also exist.
The command is `ros2 launch racer_bringup policy.launch.py policy_dir:=... raceline:=...
pose_frame:=map`, built from checked `/workspace/...` paths with no shell syntax. It goes through
every rule the other driving modes have: the pre-drive gate (recorder must be running, hard), the
override-with-reason path for the rest, the one-launch-at-a-time lock, STOP ALL, and the tracker's
own precondition (stack with localisation and a live `/pose`). A raceline must be chosen, and
with more than one accepted policy the policy must be named; a directory the check refused cannot
be selected even by name. The launch shuts down if `policy_node` exits, so a refused policy leaves
nothing running.

## Pre-drive checks and thresholds

Green, amber or red per check. A check is **required** if a drive should not start while it is not
green; optional ones are shown but never gate. Required and not green means the drive needs an
override with a reason. **Hard** checks cannot be overridden at all.

| Check | Green | Amber | Red | Required |
|---|---|---|---|---|
| Stack container | car-stack running | | not running | yes, hard |
| Bag recorder | `ros2 bag record` in `docker top` | | missing | yes, hard |
| Disk free | 15 GiB or more | 5 to 15 | under 5 | yes, hard on red |
| Battery (VESC input, 3S) | 3.70 V per cell or more (11.1 V) | 3.50 to 3.70, or above 4.25 per cell | under 3.50 (10.5 V), under 6 V total, no reading | yes |
| Safety node | `/drive` advertised by the bridge | | not | yes |
| LiDAR | `/dev/ttyUSB0` there, stack has it, `/scan` 5 Hz or more | 1 to 5 Hz | no device or no `/scan` | yes |
| VESC | `/dev/ttyTHS1` there, telemetry fresh, fault `NONE` | | no telemetry, any fault, `STALE_NO_VESC_DATA` | yes |
| Heartbeat service | `racer-heartbeat.service` active | cannot ask systemd | not active | yes |
| Temperatures | CPU and GPU under 70 C, VESC FET under 60 | 70 to 85, FET 60 to 80 | 85 and 80 | yes |
| Wi-Fi | -65 dBm or better | -65 to -75 | worse than -75 | no |
| Cameras, containers, uptime | running / states ok / over 2 min | off / odd state / just booted | | no |

All thresholds are fields of `config.Thresholds`, overridable in `/etc/racer-app/config.json`
under `"thresholds"`. The battery numbers are conservative starting values, not a measured curve
for this pack: the cell count (3) and the per-cell limits want checking against the real pack and
the VESC's own cutoff.

## Disk guard

`DiskGuard` runs every 10 s. It sheds load in order of how little it costs, and never deletes bags:

| Free space | Action |
|---|---|
| under 7 GiB | stop the cameras (nothing in the command path reads them) |
| under 3 GiB | STOP ALL (the driving launch; the stack keeps recording) |
| under 1.5 GiB | stop the stack cleanly with SIGINT so the bag closes, rather than let the disk cut it |

Starting the stack needs 5 GiB, starting the cameras 10 GiB, so the guard has hysteresis.

## Autostart

`racer-stack.service` (oneshot, `ConditionPathExists=/var/lib/racer-app/autostart.enabled`) runs
`racer-agent autostart`: wait up to 45 s for the LiDAR and VESC devices, refuse if the disk check
fails (the unit shows failed in `systemctl status`), start `car-stack` with the recorder, return.
A missing LiDAR at boot starts the stack without it and says so in the log, because docker refuses
to start a container naming a missing device. It never starts cameras and never starts a driving
launch. It does not touch `racer-heartbeat.service`. After a power cycle the stack is up and
recording with no ssh. Arming still needs the knob.

## Auth and the action log

- `racer-agent init` writes `/etc/racer-app/config.json` (mode 600) with the SHA-256 of a random
  token and prints the token once. Install prints it at the end; it is never stored in plain text
  and a re-install does not change it. `racer-agent init --rotate-token` replaces it.
- Bearer token on every `/api` route except STOP ALL; 10 wrong tokens from one address in a minute
  locks that address out for the rest of the minute; clients outside private address ranges get 403.
- `/var/lib/racer-app/actions.jsonl`: one JSON line per action, refusal, override (with its reason),
  guard action and agent start (flagging an unclean shutdown), capped at 2 MB. The UI shows the
  newest entries.

## Discovery

`racer-avahi.service.in` is installed as `/etc/avahi/services/racer.service` and advertises
`_racer._tcp` and `_http._tcp` on the configured port, next to the `racer-car.local` host name
avahi-daemon already publishes. `tools/racer_app/find_car.py` (Mac, standard library only) resolves
`racer-car.local`, confirms it with `GET /health`, and falls back to scanning the local /24 for a
host whose `/health` says `"name": "racer-agent"`; it prints the URL and opens the browser.

## Desktop app

`tools/racer_app/desktop` is a Tauri v2 app called Racer for macOS, Windows and Linux. It bundles
the same web UI (`tools/racer_app/web/dist`, no fork) and adds a thin native layer:

- **Platform layer.** `web/src/platform.ts` is the only file that knows which front it is in. In a
  browser the UI is served by the agent and uses same-origin paths and `ws://<page host>:8765`.
  Inside Tauri it is told the car's address by the Rust side and calls the agent at
  `http://<car>:8080` through `tauri-plugin-http` (the page origin is `tauri://localhost`, and the
  agent sends no CORS headers, so a plain `fetch` would be blocked). The foxglove websocket is a
  normal browser WebSocket from the page, subscribe only, same `ros.ts` as the web build.
- **Discovery** (`src-tauri/src/discovery.rs`, same order as `find_car.py`). On launch, and
  continuously after: browse mDNS for `_racer._tcp`, also resolve `racer-car.local`, and keep only
  hosts whose `GET /health` says `"name": "racer-agent"`. If that finds nothing, scan the local /24
  (64 probes at a time, 0.4 s each). One car found and none saved: it is used. Several: the picker
  lists them. The last used car is saved (address and host name, not secret) in the app data folder
  and probed first on the next launch. The connected car is probed every 4 s. If it stops answering
  the app shows "looking for the car" and searches again; it recognises the car by the host name in
  `/health`, so a Jetson that comes back on a new DHCP address is followed, and a different racer
  that takes the old address is not mistaken for it. Manual address entry (`192.168.1.50`,
  `racer-car.local:8080`) is always available and is checked against `/health` too. The scan only
  covers the /24 of the interface the OS would use to reach the LAN; on a VPN or a different subnet
  use the manual entry.
- **Token.** Kept in the OS credential store through the `keyring` crate: Keychain on macOS,
  Credential Manager on Windows, the Secret Service on Linux. The UI reads it over IPC and sends it
  as the bearer header, exactly as the web build does with localStorage. The gain over the browser
  is that it is not a plain file in the profile folder. The limit: a compromised page could ask
  for it. The page only loads the bundled UI, the capability file grants nothing but core, events
  and HTTP, and the agent itself is LAN only with a per-IP lockout. A Linux machine with no
  Secret Service keeps the token in memory for the session and asks again next launch.
- **Safety is unchanged.** The native side sends `GET /health` and nothing else. The UI subscribes
  and never publishes, so it cannot produce `/drive` or `/drive_raw`; nothing touches the mux. STOP
  ALL is the same software stop (no token needed) and the knob is still the real kill switch.
  `guard.test.ts` covers the desktop build too: no write request or command topic in any Rust file,
  the native side requests only `/health`, only `platform.ts` reaches the Tauri bridge and only for
  the listed commands, and the window capability is exactly `core:default` plus scoped HTTP (no
  file, shell or process access).

Builds (`.github/workflows/racer-desktop.yml`, separate from CI, runs only on changes under
`tools/racer_app`, no signing secrets): a check job (rustfmt, clippy with warnings denied,
`cargo test`, which compiles the Tauri project) and a bundle job per platform that uploads
artifacts: macOS `.dmg` (and the `.app` inside it), Windows `.msi` and NSIS `.exe`, Linux `.AppImage`
and `.deb`. All unsigned.

Local macOS build:

```sh
cd tools/racer_app/web && npm ci
cd ../desktop && npm ci
CI=true npx tauri build --bundles app,dmg
# result: src-tauri/target/release/bundle/{macos/Racer.app,dmg/Racer_0.1.0_aarch64.dmg}
```

`CI=true` skips the create-dmg step that asks Finder to lay out the window, which times out
without Automation permission. Needs Rust (rustup, 1.88 or newer; CI pins 1.99.1).

Tests: 28 Rust unit tests (discovery against a fake network, address parsing, the tracker following
a rebooted car, a real localhost socket for the `/health` probe, token and last-car storage), and
the platform layer and guard in vitest.

Checked on this Mac against a fake agent and foxglove socket on 127.0.0.1: the native `/health`
probe, auto-connect to a saved car, WebSocket open from the app, a keychain write/read/delete, and
an authenticated request through the HTTP plugin. NOT checked: the picker and manual-entry screens
by hand, a real mDNS answer from the Jetson, the subnet scan across a real LAN, Windows and Linux
(CI builds them, nothing has run on them), and anything against the car.

## What is and is not verified

Verified (all on the Mac, CI runs the same):

- 316 pytest tests on the agent, 99 percent line coverage. Every action against a fake docker with
  state, including the exact stack and camera argv, whitelist enforcement and injection attempts,
  auth and lockout, the LAN check, the gate (hard versus overridable, override logged), STOP ALL
  including escalation and a STOP landing mid-start, the disk guard, every check at and either side
  of every threshold, a real websocket round trip against a fake foxglove bridge, and `install.sh`
  and `uninstall.sh` run twice for real into a temporary `/etc`.
- 80 vitest tests: sign and frame conventions for the LiDAR transform, map and pose drawing, the
  CDR decode path against messages written with the real serializer, reconnects, the camera duty
  cycle, the API client, and the no-publish guard.
- The built UI was loaded against the agent in a browser on the Mac. Nothing was sent to the car.

NOT verified, in rough order of risk:

1. **Everything on the Jetson.** Docker flags are copied from the runbook, not run by the agent.
   `docker exec -d`, the pid-file stop, `docker top`, and SIGINT stopping `ros2 launch` in a
   detached exec are all assumptions until run.
2. The foxglove topic names (`/telemetry/vesc/*`, `/odom/wheel`, `/drive`, `/safety/events`, `/map`,
   `/pose`) are from `claude-docs/04-architecture.md`, not seen on a live bridge. `/map` is latched,
   so whether the bridge delivers it to a late subscriber is untested.
3. The `racer-stack.service` boot ordering (docker, USB enumeration of the LiDAR) and avahi on
   this image.
4. The tracker command needs a raceline in the localised map's frame, which does not exist yet.
5. `install.sh`'s web build inside the pinned node container on arm64.
6. Battery thresholds (above) and the camera device pick (`index` 0 of the "Global Shutter" node).

## First install on the Jetson

With the car on the bench, wheels off the ground, battery out or the knob in the kill position:

```sh
ssh racer@racer-car
cd ~/car && git fetch && git checkout feat/racer-app    # or main once merged
tools/racer_app/deploy/install.sh
```

Save the token it prints. Then from the Mac `python3 tools/racer_app/find_car.py`, or open
`http://racer-car.local:8080/`, paste the token, and walk the runbook section "Using the app".

To remove it: `tools/racer_app/deploy/uninstall.sh` (add `--purge` to delete the token and log). It
leaves `racer-heartbeat.service` and any running container alone.

## Addendum: Perception and Spiderbot patrol (2026-11-11)

Two more whitelist entries, neither loosening a rule above (tests: `agent/tests/test_perception_spiderbot.py`).

| Button | What the agent runs |
|---|---|
| Start perception | `docker run -d --name car-perception --network host --runtime nvidia --user UID:GID -e HOME=/tmp -e FASTRTPS_DEFAULT_PROFILES_FILE=... -v data/perception-cache:/tmp/.cache/racer_perception -v ~/car:/workspace -w /workspace/ros_ws car:perception bash -lc "... exec ros2 launch racer_perception perception.launch.py mode:=pose device:=cuda"`. Mode and device come from closed sets. Needs the cameras running. Drives nothing. |
| Stop perception | SIGINT, wait, rm, like the cameras. |
| Spiderbot patrol | `docker exec -d car-stack ... exec ros2 launch racer_apps spiderbot.launch.py patrol:=/workspace/data/patrols/NAME.yaml rule:=RULE speed_mps:=S output_dir:=/workspace/data/spiderbot`. NAME is a file the agent found under `data/patrols`, RULE is one of four, S is between 0.1 and 1.0 (the launch file has its own 1.0 ceiling and the vehicle_params limits on top). |

- **Disabled with a reason, never hidden.** Perception is disabled when the GPU image `car:perception`
  is not on the car (the reason names the build flags). The spiderbot is disabled when that image is
  missing, when `racer_apps` is not built in `ros_ws`, or when `data/patrols` has no patrol file.
  The reason shows next to the button and comes back in `GET /api/status` and `/api/options`.
- **The spiderbot is a driving launch.** It is the same kind of thing as the tracker: it goes through
  the pre-drive gate, the hard refusals (stack, recorder, disk, no override can change them), the
  one-driving-launch rule and STOP ALL. On top of the tracker's precondition (localisation and a live
  `/pose`) it needs `car-perception` running and `/perception/objects` live (that topic is now one of
  the rates the agent counts). It publishes `/drive_raw` only, through `safety_node`.
- **Perception runs in its own container**, never in car-stack, and starts nothing that moves.
- The recorder regex now also keeps `/perception/(objects|target|poses|detections)` and
  `/spiderbot/(alert|state|patrol_cmd)`, so a spiderbot run is reconstructable (invariant 5).
- UI: a Perception card and a patrol row in the Driving card. The UI still only calls the agent's
  HTTP API; `guard.test.ts` still passes unchanged.
