# Residual policy v0, 2026-11-11

**v0, pre-sysid. This is not the thesis result.** Phase 3 system ID has not run, so the
simulator this was trained in has not been fitted to the car. Roadmap 5.1 retrains in the
calibrated sim and supersedes everything here. v0 is a pipeline proof plus a first, honest look
at whether a residual helps in sim at the real car's scale. Nothing below is a claim about the
real car.

## Result in one paragraph

The residual changes lap time by about 1% (faster) on laps both arms complete, consistently
across 120 paired episodes, and does not improve completion. On unseen draws of the training
track families completion was 94.2% with the residual against 95.8% for the tracker alone
(not distinguishable at n=120). When every randomisation range is widened 1.5x it is worse
(75.8% against 83.3%). Cross-track error is a little larger with the residual. So: a small
speed gain at the price of a little margin, in a sim that is not the car. That is a valid,
unexciting result, and the honest summary is "no clear benefit yet". Full-authority residuals
(4x the final authority of the quarter config below) did clearly worse than the tracker.

## Bugs and defects found on the way

- **The S.3 env had no walls.** `Track.from_refline` builds an all-free map, so nothing could
  crash and LiDAR saw nothing. v0 uses the bridge's `build_corridor_occupancy` (imported by path,
  `sim/bridge` is untouched).
- **f1tenth_gym's own start-gate `terminated` fires after about one lap.** Treating it as
  terminal truncates episodes and zeroes the value bootstrap. The env now ignores it and ends on
  a wall contact or the episode's own lap target. Test: `test_upstream_start_gate_does_not_terminate_training_episodes`.
- **S.3 trained on raw observations but recorded running statistics in the contract**, so a node
  that applied the contract's normalisation would have fed the network unseen inputs. v0 freezes
  the statistics, bakes them into `policy.pt`, and writes the contract's own block as the
  identity (see "Deploy" for why).
- **The S.1 placeholder tyre is far from the car.** `racer_gym/params.py` feeds the gym's
  `C_Sf = 4.7` (a dimensionless coefficient in the gym's own model) into a Pacejka curve as N/rad.
  The result is a 1.8 m turning radius at full lock and 2 m/s where the car measured 0.60 m.
  Not changed here (it would move the S.6 references, which is a human decision); v0 randomises
  cornering stiffness over 80 to 400 N/rad, which reproduces about 0.65 m at 1 m/s. Worth fixing
  when sysid lands. (Fixed afterwards: see `sim-tyre-fix-2026-11-11.md`; v0 numbers re-run, unchanged.)
- The S.3 safety layer is not in the loop, so "brakes" below are a proxy (see caveats).

## Setup

**Real-car numbers (2026-11-10), applied as in-memory overrides, not written to
`config/vehicle_params.yaml`** (that is on `calib/2026-11-10`): steering limit left 0.504 rad,
right 0.449 rad (committed symmetric 0.4189); top speed 2.08 m/s (`throttle_full_scale_mps`
2.91 corrected by 1.401x); overhangs front 0.11 m, rear 0.14 m; stop latency 0.13 s.
`max_acceleration_mps2: 3.0` is a provisional assumption (it only sets the envelope's per-step
speed rate limit). Wheelbase 0.3302 m is already committed.

**Base controller.** The tracker is the evaluation baseline, so it was tuned before any
learning: four grid passes over lookahead range, curvature reference, raceline lateral
acceleration and top speed, under the full randomisation, scored by mean speed with a miss
counting as zero and a completion floor of 90%. Budget: 17,856 two-lap episodes, 0.6 CPU hours
(161 s of wall clock on 13 workers). A first pass with a planner bug was discarded. Chosen:
lookahead 1.0 to 1.3 m, curvature reference 1.0 1/m, raceline `a_lat` 3.5 m/s2, top speed
2.0 m/s; about 93% completion on the tuning pool. The tracker's stock 0.4 to 1.5 m lookahead
oscillated at 2 m/s with 0.1 s of steering lag. These are SIM-tuned values: a deployed run
must launch the tracker with the same ones. Roadmap Phase 4 tunes on hardware.

**Reference line.** A 1 m lane with inner radius under 0.7 m cannot be followed along its
centreline (minimum turning radius about 0.60 m), so the line is pushed outward through tight
turns (offset capped at 0.25 m) before the committed `tools/raceline` pipeline adds the speed
profile. Not an optimal raceline.

**Randomisation, per episode.** Ranges are guesses centred on the measurements, not fits.

| Quantity | Range | Why |
|---|---|---|
| Friction mu | 0.55 to 1.1 | living-room floor, foam board, unknown tyre compound |
| Cornering stiffness, front (N/rad) / rear ratio | 80 to 400 / 0.8 to 1.3 | reproduces the measured turning radius at low speed; understeer at speed unknown |
| Mass scale | 0.85 to 1.20 | battery and mounting changes |
| Steering limit left / right (rad) | 0.46 to 0.52 / 0.41 to 0.47 | about 8% around the 0.504 / 0.449 measurements |
| Steering gain / bias (rad) | 0.92 to 1.08 / -0.03 to 0.03 | servo scale and trim error |
| Speed scale (command to speed) | 0.90 to 1.10 | the ERPM-cap scale error was 1.4x once already |
| Top speed (m/s) / accel limit (m/s2) | 1.95 to 2.20 / 1.5 to 5.0 | measured 2.08; accel unmeasured |
| Steering tau / throttle tau (s) | 0.02 to 0.10 / 0.05 to 0.30 | unmeasured (null in vehicle_params) |
| Command delay (s), shared by both channels | 0.03 to 0.13 | 0.13 s measured stop latency is the top end |
| Speed noise, bias | 0.02 to 0.08, +-0.05 m/s | |
| Yaw-rate noise, bias | 0.01 to 0.05, +-0.03 rad/s | |
| Pose error (AR(1), about 1 s) | 0.005 to 0.03 m, 0.005 to 0.04 rad | the localiser is not working on the car yet; this is a guess |
| LiDAR noise, dropout, refresh period | 3 to 20 mm, 0 to 3%, 4 to 6 steps | RPLidar C1 is about 10 Hz, policy 50 Hz |
| Extra observation latency | 0 to 0.06 s | |

Track pools use seeds 1000+ (train, 80 tracks), 3000+ (base tuning), 5000+ (validation),
10000+ and 20000+ (held-out). Episode seeds are disjoint too (`test_heldout_report.py`).

**Training.** SAC (stable-baselines3), 128x128 MLP, gamma 0.99, buffer 1M, one gradient step per
env step, observations normalised by frozen statistics, reward unchanged from S.3 (progress, crash,
envelope violation; the crash weight went from 10 to 50, a weight on an existing term, not a new
term). The residual is bounded by the envelope: the final config allows +-0.024 rad steering and
+-0.10 m/s speed (fractions 0.025 and 0.004 of the committed ranges, so the bound is the same under
the committed `vehicle_params`). TensorBoard logs and checkpoints are under
`/Users/cameronjim/code/car-data/training/v0/`. Throughput about 270 steps/s per run on this Mac
with six runs at once.

| Stage | Runs | Steps | Finding |
|---|---|---|---|
| Pilots (300k each) | full authority (0.10 / 0.016), plus crash weight 50, gamma 0.99, bigger net, half authority | 4 x 300k | all worse than the tracker on completion (62 to 82% against 95%); less authority and a bigger crash weight helped |
| Final | "half" authority (0.05 / 0.008) and "quarter" (0.025 / 0.004), 3 seeds each | 6 x 2M of a planned 4M | validation flat after about 500k steps, so stopped at 2M; about 2 h wall |

Total training compute: 13.3M env steps. Validation score (64 paired episodes, never the test
pools) picked the checkpoint: quarter config, seed 2, step 1,000,000. Validation lap-time
change across all quarter checkpoints was -0.9% to -2.0%, completion equal to or 2 points below
the tracker. Half authority checkpoints were all worse than the tracker on validation (best
-0.068 score, completion 84% against 91%).

## Held-out evaluation (sim, 120 paired episodes per condition, 2 laps from a standing start)

Both arms get the identical world (track, direction, draw, noise, start) and go through the same
envelope and the same 2.0 m/s cap. Policy loaded through `racer_policy.load_contract`,
`verify_against_environment` and `load_model`, fed raw observations.

| Condition | Completion, tracker | Completion, tracker + residual | Paired lap time (completed by both) |
|---|---|---|---|
| held-out draws of training shapes | 115/120 (95.8%) | 113/120 (94.2%) | -1.43% (CI -1.57 to -1.29) |
| unseen shapes (curves, large ovals) | 120/120 | 120/120 | -0.61% (CI -0.69 to -0.53) |
| ranges widened 1.5x | 100/120 (83.3%) | 91/120 (75.8%) | -1.21% (CI -1.36 to -1.08) |
| nominal (no randomisation) | 120/120 | 120/120 | -1.64% (CI -1.79 to -1.48) |

Other metrics, held-out draws condition (tracker / residual): mean lap time 6.18 s / 6.10 s;
mean absolute cross-track error 0.077 m / 0.086 m; crashes 5 / 7; TTC-proxy engagements per
episode 11.4 / 11.2; residual clipped by the envelope 0% / 0%; steps rate-limited 10.8% / 11.3%;
OOD fallback 0.24% / 0.24%. Wilson 95% for the completion rates are 91 to 98% and 88 to 97%.
The bootstrap intervals are over episodes in sim and say the lap-time difference is consistent
across worlds; they say nothing about the car. Both direction breakdowns are in
`eval_summary.json` (`by_direction`). Per-episode data and tables:
`/Users/cameronjim/code/car-data/training/v0/final/heldout_chosen/`; a summary copy is committed
at `training/policies/v0-2026-11-11/heldout_summary.json`.

## Policy directory and the deployment contract

`/Users/cameronjim/code/car-data/policies/v0-2026-11-11/` holds `policy.pt` (105 KB, 22,914
parameters, sha256 `3a7fd7fe...938b`), `contract.yaml` and `policy_meta.yaml`. Only the two small
text files and a pointer are committed (`training/policies/v0-2026-11-11/`); the repo commits no
model binaries.

- `racer_policy.load_contract` and `verify_against_environment` accept it against the committed
  `vehicle_params` and the env's live observation schema, `load_model` loads it, and the held-out
  report above ran entirely through that path.
- Refusals still refuse. `tests/test_policy_export.py` (nightly, torch) shows this exact kind of
  directory is rejected for a flipped byte in `policy.pt` (checksum), a future
  `contract_version`, a different `sysid_session_id`, a different `schema_version`, wrong
  units on an observation field, and swapped field order. The `racer_policy` suite (27 tests) is
  unchanged and green. No tolerance, schema or loader was touched.
- The contract schema is `additionalProperties: false`, so v0 labelling and everything the schema
  cannot hold live in `policy_meta.yaml`. The loader does not read it, so its
  `must_match_at_deploy` section is not enforced automatically: the deploy node must check it.
- `contract.yaml`'s `normalization` block is the identity on purpose: the real statistics (in
  `policy_meta.yaml`) are applied inside `policy.pt`, which takes the raw observation in the
  contract's units. A node that normalised again would break the policy, so nothing should.
- `vehicle_params` reference is `schema_version 0.13.0`, `sysid_session_id none-preliminary`. If
  `calib/2026-11-10` bumps either, the loader will refuse this policy. That is the contract
  working; do not edit the yaml to get past it. Re-export is a human decision.

## Inference latency

CPU, TorchScript, one thread, single observation, 20,000 calls on this Apple Silicon Mac: mean
8.5 us, p50 8.7 us, p99 9.2 us, p99.9 22 us, max 58 us; budget is 20,000 us at 50 Hz. The model
is 22.9k parameters (about 46 kFLOP per call), so the cost is framework overhead, not
arithmetic. The Jetson figure is an ESTIMATE, not a measurement: assume the Orin Nano's Arm
cores are 5 to 15x slower on this kind of small eager-mode call, so roughly 50 to 150 us, plus
Python and ROS observation assembly that this tool does not time. Even 100x slower would be 1 ms.
Run `uv run python -m racer_train.latency --policy-dir <dir>` on the Jetson for the real number.

## Caveats

- **Pre-sysid sim.** Tyre, actuator lag, delay, mass and surface values are guesses; the sim
  was never validated against a car trajectory.
- **The result is marginal.** About 1% faster on completed laps, no completion gain, worse
  out of range. The two arms differ only by +-0.024 rad and +-0.10 m/s.
- **TTC "brakes" are a proxy.** `racer_safety` is C++ and not in the loop. The count is forward
  LiDAR clearance over speed against the committed thresholds, useful only to compare arms.
- **The base was tuned in sim** on a pool that overlaps the training distribution; the real
  tracker is untuned on hardware.
- **The observation needs a live builder.** The policy was trained on a 270 degree, 1080-beam scan
  min-pooled into 36 beams of 7.5 degrees, clipped at 5 m, refreshed at 8 to 12 Hz. The car's
  RPLidar is 360 degrees and about 500 beams. The deploy-side builder must resample to the
  contract's `lidar` block exactly, or the loader refuses. The pose-derived fields assume a
  working localiser, which the car does not have yet.
- Seed spread: on validation the three quarter-authority seeds scored +0.02, +0.02, -0.004;
  only the chosen seed was run on the held-out pools.

## Deploy, next session

Not possible end to end yet, for two reasons that are scope, not oversight:

1. **There is no `policy_node` and no `policy.launch.py`.** That is roadmap 5.2, behind gate G3,
   so it was not started. The app's ML policy button needs both.
2. The tracker has no pose on the car until localisation works.

What is ready, and the convention to use:

1. The app's agent looks in `<repo checkout on the car>/data/policies/<name>/` for a directory
   whose `contract.yaml` passes `racer_policy.load_contract` (branch `feat/racer-app`, `Settings.
   policies_dir`). Copy or symlink, on the car:
   `mkdir -p data/policies && cp -r <car-data>/policies/v0-2026-11-11 data/policies/`
   (`data/` is gitignored). The directory name is what the button will show.
2. Check the policy on the car's checkout before anything moves:
   `uv run python -m racer_train.latency --policy-dir data/policies/v0-2026-11-11` and a
   `load_contract` plus `verify_against_environment` against the live `vehicle_params`; any
   refusal stops here.
3. Launch the tracker with lookahead 1.0 to 1.3 m, curvature reference 1.0, on a raceline built
   with `a_lat` 3.5 and top speed 2.0, and give the future node the envelope settings in
   `policy_meta.yaml` `must_match_at_deploy` (speed cap 2.0 m/s, residual fractions 0.025 and
   0.004, OOD threshold 3.0 and its reference and scale, action scales).
4. First runs follow the standing rules: wheels off the ground, two people, driver on the RC
   kill, bagged with rail voltage. The first number to record is the zero-shot comparison,
   report only (roadmap 5.2).

## Reproduce

`git` SHA `f396aef` (training code) plus `training/configs/v0/sac_residual_v0_quarter_0.1.0.yaml`
plus seed 2, checkpoint 1,000,000; `policy_meta.yaml` records the config hash. Train:
`uv run python -m racer_train.train --config <yaml> --seed 2 --output-dir <dir>`; tune the base:
`racer_train.tune_base`; select: `racer_train.select_checkpoint`; evaluate:
`racer_train.heldout_report`. Tests: `uv run pytest` in `training/racer_train` (125 per-push) and
`uv run pytest -m slow` (export, loader refusals, parity, checkpoint re-export; nightly).
